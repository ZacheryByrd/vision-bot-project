# vision_bot v2: Fleet-Connected Autonomous Navigation

**Audience:** Claude Code, working inside the existing `vision-bot-project` repo.
**Owner:** Zach. **Status of v1:** shipped (line-following rover, ROS2, Gazebo, rosbridge/Next.js dashboard).
**Goal of v2:** extend the same robot into an autonomous mobile robot with SLAM, localization, Nav2, a custom C++ Nav2 plugin, two namespaced robots, and a bridge to the separate Robot Fleet Management System so goals can be sent from the dashboard.

---

## 0. Operating rules (read before doing anything)

1. **Discover before you build.** Section 1 is mandatory. Do not assume ROS distro, Gazebo version, package names, topic names, or API endpoints. Read the repo and the machine first and write findings to `docs/V2_DISCOVERY.md`.
2. **Never break v1.** The existing line-follow demo (`sim_launch.py`, `perception_node`, `motor_control_node`, dashboard) must still work after every phase. New work goes in new packages and new launch files. Edits to existing files must be minimal, justified in the commit message, and covered by the v1 regression check (section 2).
3. **One phase at a time, with a gate.** Each phase ends with a verification gate. Do not start the next phase until every gate item passes. If a gate fails, fix it or stop and report. Never mark a phase done on "it should work".
4. **Never fabricate results.** Every number in a README or doc (localization error, success rate, time to goal) must come from a script in the repo that you actually ran. Save raw outputs to `benchmarks/results/`. If you did not run it, write "not measured yet".
5. **Do not guess package or command names.** If something fails, read the error, run `ros2 pkg list | grep <name>`, `apt-cache policy ros-$ROS_DISTRO-<pkg>`, or check the package's docs. Never invent flags or parameters.
6. **Use sim time everywhere.** Every node in simulation gets `use_sim_time: true`. Mixed clocks cause silent TF and costmap failures.
7. **Secrets:** no credentials, tokens, or `.env` contents in git. Use environment variables and commit only `.env.example`.
8. **Git hygiene:** work on a branch per phase (`v2/phase-1-sensors`, etc.), small commits, imperative messages. Never force-push. Never commit build artifacts (`build/`, `install/`, `log/`, large bags). Large maps and bags go through Git LFS or are regenerated by a script. Ask Zach if unsure.
9. **Ask instead of assuming** when a decision is Zach's (for example, scope cuts, hardware purchases, changing the fleet repo's public API). Otherwise decide, document the decision in `docs/DECISIONS.md` (date, choice, reason), and continue.
10. **Report at each gate:** what changed, exact commands run, results, what is left. Keep it short and factual.

## 2. Target architecture

```
                    +------------------------- Fleet Platform (existing) --------------------------+
                    | FastAPI + PostgreSQL + Next.js  (JWT auth, RBAC)                              |
                    | robots, missions, goals, telemetry                                            |
                    +----------------------^------------------------------^-------------------------+
                                           | REST (+ WebSocket if available)
                                  +--------+--------+            +--------+--------+
                                  | fleet_bridge    |            | fleet_bridge    |
                                  | /robot1         |            | /robot2         |
                                  +--------+--------+            +--------+--------+
                                           | NavigateToPose action, pose, status, battery
   /robot1: lidar, imu, odom -> EKF -> AMCL(map) -> Nav2 -> twist_mux -> diff drive
   /robot2: same stack, own namespace and own TF tree, shared saved map
   v1 perception + motor_control (line follow) remain available as one input to twist_mux
```

**New packages (leave existing packages untouched except where stated):**

| Package | Type | Contents |
|---|---|---|
| `vision_bot_nav` | ament_python or ament_cmake (launch only) | launch files, Nav2/SLAM/EKF/twist_mux params, maps, RViz configs, worlds for navigation |
| `vision_bot_plugins` | ament_cmake (C++) | custom Nav2 costmap layer plugin(s) |
| `fleet_bridge` | ament_python | ROS2 node bridging a robot to the fleet API |
| `benchmarks/` (plain dir) | scripts | goal-success, localization-error, plugin A/B benchmarks, results |

**Command velocity ownership (critical):** all velocity sources publish to their own topic. `twist_mux` selects one and publishes the final command to the topic the diff-drive plugin listens on. Priorities: teleop (highest) > line_follow > navigation. Nothing else publishes to the final topic.

**TF ownership (critical):** exactly one node publishes each transform.
- `odom -> base_link`: robot_localization EKF (disable the diff-drive plugin's TF publishing, keep its odometry topic).
- `map -> odom`: AMCL (localization) or slam_toolbox (mapping), never both at once.
- Static sensor frames: `robot_state_publisher` from the URDF.

## 3. Phase 1: Sensors, command mux, and a navigable world (Week 1)

**Branch:** `v2/phase-1-sensors`

1. **Create `vision_bot_nav`** with the standard package layout.
2. **Update the robot model.** Prefer a *copy* (`vision_bot_nav/urdf/vision_bot_nav.urdf.xacro`) that includes or extends the v1 model, so v1 is untouched. Add:
   - 2D lidar link and sensor publishing `sensor_msgs/LaserScan` on `scan` (about 360 samples, range roughly 0.12 to 8 m, 10 Hz, realistic noise).
   - IMU link and sensor publishing `sensor_msgs/Imu` on `imu` with modest noise.
   - **[Classic]** `libgazebo_ros_ray_sensor.so` and `libgazebo_ros_imu_sensor.so` plugins.
   - **[New Gazebo]** `gpu_lidar` and `imu` sensors, the world-level `Sensors` and `Imu` system plugins, and a `ros_gz_bridge` config bridging `/scan` and `/imu`. Headless runs may need a virtual display or the `ogre2` engine configured correctly.
   - Set the diff-drive plugin to **not** publish the `odom -> base_link` TF (it should still publish `odom`). Confirm with `view_frames` that no duplicate publisher exists.
3. **New world** `vision_bot_nav/worlds/nav_world`: an enclosed area (roughly 10 x 10 m) with walls, 2 to 3 rooms or corridors, and several box/cylinder obstacles with distinct geometry (symmetric rooms confuse localization). Keep the v1 `track.world` as is.
4. **`twist_mux`:** create `config/twist_mux.yaml` with three topics (`cmd_vel_teleop` priority 100, `cmd_vel_line` priority 20, `cmd_vel_nav` priority 10, each with a 0.5 s timeout). Remap twist_mux output to the diff-drive input topic. Verify the message type (Twist vs TwistStamped) matches your distro's twist_mux and diff-drive.
5. **Wire v1 into the mux:** remap `motor_control_node`'s output to `cmd_vel_line` through the *launch file* (a remap, not a code change). If a code change is unavoidable, make the topic name a parameter with the old name as default.
6. **Launch file** `nav_sim.launch.py`: starts the sim, spawns the robot in the new world, robot_state_publisher, bridge (New Gazebo), twist_mux, and optional teleop publishing to `cmd_vel_teleop`.

**Gate 1 (all must pass):**
- [ ] `ros2 topic hz /scan` and `/imu` show the expected rates.
- [ ] RViz shows the scan matching the walls in the world.
- [ ] `view_frames` shows a single parent for every frame, no TF warnings in logs.
- [ ] Teleop drives the robot through twist_mux; publishing on `cmd_vel_line` also drives it; teleop overrides line_follow.
- [ ] `scripts/check_v1.sh` passes.

## 4. Phase 2: SLAM and EKF (Week 2)

**Branch:** `v2/phase-2-slam-ekf`

1. **EKF** (`robot_localization`, `ekf_node`): config in `vision_bot_nav/config/ekf.yaml`.
   - `two_d_mode: true`, `world_frame: odom`, `odom_frame: odom`, `base_link_frame: base_link`, frequency about 30 Hz, `use_sim_time: true`.
   - Start minimal: `odom0` fusing linear x velocity and yaw velocity; `imu0` fusing yaw velocity. Add more only if it measurably helps.
   - EKF publishes `odom -> base_link` and the filtered odometry topic.
2. **slam_toolbox** in online async mode with a params file: set `odom_frame`, `base_frame`, `map_frame`, `scan_topic`, `use_sim_time`. Launch via `slam.launch.py`.
3. **Map the world** by teleop. Save with `nav2_map_server`'s `map_saver_cli` to `vision_bot_nav/maps/nav_world.{yaml,pgm}`. Also save the slam_toolbox serialized pose graph if you plan to use it later.
4. **Ground truth for evaluation:**
   - **[Classic]** `libgazebo_ros_p3d.so` publishing true pose.
   - **[New Gazebo]** pose/odometry publisher system bridged to ROS.
   Ground truth is used only by benchmark scripts, never by the navigation stack.
5. **Benchmark script** `benchmarks/odom_drift.py`: drive a fixed route (scripted or from a recorded bag), compare raw odometry vs EKF output vs ground truth. Report mean and max position error and final drift in a table. Save CSV and a plot.
6. **Add noise/slip** to the simulated odometry (or wheel friction) if raw odom is unrealistically perfect; otherwise the EKF comparison shows nothing. Document the noise parameters.

**Gate 2:**
- [ ] The saved map visually matches the world (check in RViz and the PGM).
- [ ] No TF errors; `map -> odom -> base_link` chain is valid during SLAM.
- [ ] `benchmarks/odom_drift.py` ran and produced `benchmarks/results/odom_drift_*.csv` with real numbers.
- [ ] `check_v1.sh` passes.

## 5. Phase 3: Nav2 on the saved map (Week 3)

**Branch:** `v2/phase-3-nav2`

1. Copy and adapt Nav2 params from the distro's `nav2_bringup` defaults into `vision_bot_nav/config/nav2_params.yaml` (do not write from memory; start from the installed file and diff).
2. Set robot footprint/radius from the URDF, `robot_base_frame`, `odom` topic to the EKF output, scan topic, `use_sim_time`, and map file path.
3. **Localization:** `map_server` + `amcl` + lifecycle manager (use `nav2_bringup`'s localization launch where possible). Set the initial pose via parameter or `/initialpose`.
4. **Velocity routing:** point Nav2's final velocity output to `cmd_vel_nav` so it enters twist_mux. In some distros the chain includes `velocity_smoother` and `collision_monitor`; follow the installed bringup's topic chain and verify each hop with `ros2 topic info -v`.
5. **Tune** costmap inflation radius, controller speeds, and goal tolerances until the robot is reliable. Record the final values and why in `docs/TUNING.md`.
6. **Navigation benchmark** `benchmarks/nav_goals.py`: sends N goals (N >= 10, spread across rooms, defined in a YAML file) through the `NavigateToPose` action, with a per-goal timeout. Records success/fail, time to goal, path length, final position error vs ground truth, and recoveries triggered. Output CSV + markdown summary.

**Gate 3:**
- [ ] With the stack running, a goal sent from RViz is reached.
- [ ] `nav_goals.py` with 10 goals completes; success rate is recorded honestly (target is at least 9 of 10, but record whatever it is and tune further if lower).
- [ ] Teleop still overrides Nav2 through twist_mux.
- [ ] `check_v1.sh` passes.

## 6. Phase 4: Custom C++ Nav2 plugin (Week 4)

**Branch:** `v2/phase-4-plugin`

**Default plugin: `RobotAvoidanceLayer`** (a `nav2_costmap_2d::Layer`). It subscribes to other robots' poses and adds a cost footprint around them so a robot plans around its teammates. This is the piece that makes the multi-robot story real, and it is benchmarkable.

1. Create `vision_bot_plugins` (`ament_cmake`) depending on `nav2_costmap_2d`, `pluginlib`, `rclcpp`, `rclcpp_lifecycle`, `geometry_msgs`, `nav2_util`. Follow the distro's `nav2_costmap_2d` layer interface exactly (`onInitialize`, `updateBounds`, `updateCosts`, `reset`, `onFootprintChanged`, `isClearable`). Read the existing `nav2_costmap_2d` layers in the installed source or docs as the reference rather than writing from memory.
2. Parameters (declared with defaults): `robot_pose_topics` (list), `robot_radius`, `cost_scaling`, `max_pose_age_s`, `enabled`.
3. Behavior: keep the latest pose per topic; ignore stale poses (older than `max_pose_age_s`); transform into the costmap frame; mark cells within a radius as lethal or high cost with a decaying gradient. Be careful with thread safety (callbacks vs `updateCosts`); use a mutex.
4. Export with `pluginlib` (`plugins.xml`, `pluginlib_export_plugin_description_file`). Register the layer in `nav2_params.yaml` for the local and/or global costmap.
5. **Tests:** gtest unit tests for the cost computation (pure function separated from ROS plumbing), plus a launch test confirming the plugin loads without errors. `colcon test` must pass.
6. **A/B benchmark** `benchmarks/plugin_ab.py`: with the second robot present (can be done early with a stationary or scripted second robot, then rerun in phase 5), run the same scenarios with and without the layer: crossing paths, a robot parked in a corridor. Metrics: goal success, time to goal, minimum distance to the other robot, number of recoveries. Same goals, same seeds, N >= 10 per condition.
7. **Stretch (only after the gate):** a custom controller plugin. Do not start it unless Zach asks.

**Gate 4:**
- [ ] Plugin builds with no warnings treated as errors; `colcon test --packages-select vision_bot_plugins` passes.
- [ ] Nav2 loads the layer (check lifecycle logs); the layer is visible in RViz.
- [ ] `plugin_ab.py` produced real comparison numbers (even if the layer is not better; report honestly).
- [ ] `check_v1.sh` passes.

## 7. Phase 5: Two robots and the fleet bridge (Week 5)

**Branch:** `v2/phase-5-fleet`

### 7.1 Second robot with namespaces
- Follow the installed `nav2_bringup` multi-robot reference launch (for example the multi-robot simulation launch in `nav2_bringup`) instead of designing namespacing from scratch.
- Each robot: its own namespace (`robot1`, `robot2`), its own Nav2 instance, AMCL, EKF, twist_mux, and robot_state_publisher; **its own TF tree** (remap `/tf` and `/tf_static` to namespaced `tf` and `tf_static`) with frames unprefixed within each tree, sharing the single saved map.
- Different spawn poses and different initial poses for AMCL.
- Update RViz configs and the benchmarks to take a robot namespace argument.
- Update the sensor bridge config (New Gazebo) per robot and ensure unique sensor/model names.

### 7.2 `fleet_bridge` node (one per robot, parameterized by namespace and robot ID)
Responsibilities:
1. **Authenticate** to the fleet API using the platform's real auth flow (JWT with refresh-token rotation). Use a dedicated service/robot account via environment variables. Handle token expiry by refreshing, and re-login on failure. Never log tokens.
2. **Register** the robot (create or fetch by ID) on startup.
3. **Report telemetry** at a modest rate (about 1 Hz): pose in the map frame (from the robot's TF tree), navigation state (idle, navigating, failed), battery (simulated value that drains with distance, clearly labeled simulated), timestamp.
4. **Receive goals:** poll or subscribe (use a WebSocket/SSE if the platform has one, otherwise poll every 1 to 2 s). On a new goal, send a `NavigateToPose` action goal, report status transitions (accepted, succeeded, failed, canceled) back to the API.
5. **Cancel:** support cancel from the platform.
6. **Resilience:** if the API is down, keep running, buffer or drop telemetry (bounded), retry with exponential backoff; if ROS/Nav2 is down, report that status. Never crash the bridge on a network error.
- Use only endpoints that exist. If the fleet API lacks needed endpoints (for example goals/missions per robot), propose the minimal addition to Zach before editing the fleet repo, then add them with tests, RBAC on each endpoint (consistent with the existing pattern), and migrations if schema changes.
- Unit-test the bridge with a mocked HTTP layer (pytest) and a mocked action client. Add a `.env.example`.

### 7.3 Dashboard map view
- Show the saved map as a static image (convert PGM to PNG once, with map metadata for the pixel-to-world transform; do not stream the occupancy grid over rosbridge continuously).
- Overlay each robot's pose (from fleet telemetry or rosbridge), an orientation arrow, and status.
- Click a point on the map to set a goal; choose robot (or "nearest idle"); send through the fleet API (not directly to ROS), so the whole path is exercised.
- Keep existing dashboard features (MJPEG, telemetry, manual/auto toggle, reconnect) working.
- Get the pixel-to-world transform right: map resolution, origin, and the image's flipped y-axis. Add a unit test for the conversion with known points.

**Gate 5:**
- [ ] `ros2 node list` shows two independent stacks under `/robot1` and `/robot2`; no cross-talk on `cmd_vel`.
- [ ] Both robots localize on the shared map and each reaches goals independently.
- [ ] Clicking a point in the dashboard makes the chosen robot drive there; the fleet platform shows the status changes.
- [ ] `plugin_ab.py` rerun with two real robots; results saved.
- [ ] Bridge survives: API restart, expired token, Nav2 goal rejection.
- [ ] `check_v1.sh` passes.

## 8. Phase 6: CI, regression tests, and docs (Week 6, optional but recommended)

**Branch:** `v2/phase-6-ci-docs`

1. **Rosbag replay regression test:** record a bag of `/scan`, `/imu`, `/odom` (or raw wheel data), `/tf_static`, and ground truth from a standard mapping/navigation run (keep it small; use compression; store with Git LFS or generate in a release artifact). A script replays it with `use_sim_time`, runs the EKF (and localization), and computes error against the ground truth in the bag. The test fails if error exceeds a threshold set from your measured baseline plus a margin. Document how the baseline was chosen.
2. **GitHub Actions workflow:** use a ROS Docker image matching the distro; build with colcon, run `colcon test`, run unit tests for the bridge and plugin, run the replay regression test. Do not try to run full GUI Gazebo in CI; keep CI headless and deterministic. Cache dependencies.

## 9. Known pitfalls (check these first when something is broken)

| Symptom | Likely cause |
|---|---|
| Robot jitters or TF warnings about extrapolation | Duplicate `odom -> base_link` publishers (diff-drive plugin and EKF both on), or `use_sim_time` missing on a node |
| Nav2 never becomes active | Lifecycle manager did not start a node; wrong map path; `map -> odom` missing because AMCL has no initial pose |
| Costmap empty or wrong | Wrong scan topic or frame; scan frame not in the TF tree; clock mismatch |
| Robot ignores Nav2 commands | Wrong topic chain into twist_mux; twist_mux timeout too short or a higher-priority source is still publishing (including zero-velocity messages from v1's node) |
| v1 node fights navigation | v1 `motor_control_node` publishes zeros when no detection; it is on a higher priority than navigation. Fix by gating v1 output (publish only when line following is enabled) or reordering priorities, and document it |
| Namespaced robot has no TF | `/tf` not remapped to the namespaced topic, or RViz/bridge listening on global `/tf` |
| Localization jumps between rooms | Symmetric world, bad initial pose, or too few lidar features |
| Lidar publishes nothing in headless New Gazebo | Sensors system plugin missing or no rendering backend available |
| Dashboard goals land in the wrong place | Map origin/resolution/y-flip error in the pixel-to-world conversion |
| Bridge works once then 401s | Access-token expiry or refresh-token rotation not handled (old refresh token reused) |

## 10. Definition of done for v2

1. Two simulated robots map, localize, and navigate autonomously using Nav2 on a shared map.
2. A custom C++ Nav2 costmap layer is built, unit tested, loaded by Nav2, and benchmarked against the stock configuration.
3. An EKF fuses odometry and IMU, and its improvement over raw odometry is measured against ground truth.
4. A goal clicked on the dashboard map flows through the fleet API and `fleet_bridge` to the right robot, and status flows back.
5. v1 line-following still works and is selectable through twist_mux.
6. CI runs build, unit tests, and a rosbag replay regression test.
7. README has an architecture diagram, demo GIF, reproducible commands, and real benchmark numbers.
